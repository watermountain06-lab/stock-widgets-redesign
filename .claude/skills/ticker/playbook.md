# Add-Ticker Playbook

Distilled from the NVDA → AAPL → GOOGL build sessions. This file is the live execution spec — keep it in sync with reality as the process changes, (The old live-repo pipeline and its Codex `stock-add`/`stock-refresh` skills were retired on 2026-09-11 - see the first boundary below.)

So a fix to an existing card goes to preview and arrives here through that script; do not hand-edit a card here and expect it to survive. (Superseded 2026-09-12; this line used to say push it like any other change.) A `/ticker` build agent should run no `git` command at all — the coordinating session commits after the agent signals it is done editing, and re-checks `git status` afterwards, because a done signal is the agent's intent and not a guarantee about the files. Still always use Codex **text mode** (`codex exec --skip-git-repo-check -`), not code-mode `codex review`, to keep the review workflow consistent across this file's tab-by-tab passes.
- **Never fabricate a number.** Every figure needs a real source: SEC 10-Q/10-K/XBRL for financials, StockAnalysis.com for analyst ratings, WebSearch with a real article link for news events. If a figure can't be verified, say so in the card rather than inventing a plausible-looking one.
- **Never hand-type a numeric array** (price/MA series, financial time series) into HTML/JS. Always splice it from the source JSON via a Python script and write the JS literal programmatically. Hand-retyping has caused real length-mismatch bugs before.
- **Autonomous mode (2026-08-25 on, per explicit user request):** no per-card chat confirmation. Pull up the legacy widget's existing content (if any, in `prototypes/legacy/`) or research from scratch, then decide what to keep/cut/rebuild yourself using the documented judgment criteria throughout this file (capital-allocation criterion, itemize-vs-synthesize rule, GAAP-distortion handling, etc.) and build straight through. The automated safety checks below are NOT optional and replace the old chat-approval gate — they are what actually catches mistakes now: Codex text-mode review every tab, full browser verification every tab, never fabricate a number, never hand-type a numeric array, never depend on the retired old repo. Summarize every judgment call made (ticker-selection rationale, peer/anchor choice, GAAP handling, any new #news event added, Bull/Bear content) in the Step 6 wrap-up so the user can review after the fact rather than approving before the fact.

## Context/token efficiency (added 2026-08-31, applies to every step below)

`{TICKER}_full_widget.html` is 200KB+ (a full `Read` burns 20K+ tokens in one call). This applies to whoever is touching the file — a `/ticker` build agent AND a human-driven session doing a post-hoc fix/review pass on an already-built card.

- **Never `Read` the whole widget file.** Locate the target section with `grep -n "..."` first, then either `sed -n 'X,Yp'` via Bash or `Read` with a narrow `offset`/`limit` around the matched line numbers. This is how every targeted edit in this repo should be located, full stop — not just for builds.
- **Browser verification: one screenshot per tab, taken after the layout has settled** (post-scroll, post-interaction) — not one per scroll step or per intermediate state. Use the `zoom` action to inspect a specific small region closely instead of taking a fresh full-page screenshot.
- **Codex review payload, round 2+: send only the diff**, not the full tab+data package again. Round 1 sends the complete package (HTML + JS data object + 검증된 원본 데이터 block, per Step 4 below); if Codex flags issues and a round 2/3 is needed, package just the changed lines plus the specific facts needed to re-verify them — not the whole tab from scratch.
- **SEC EDGAR `companyconcept` responses**: the API returns the ticker's *entire* historical XBRL series for a tag, often hundreds of entries. Pipe `curl`'s output through a filter (`python3 -c` or `jq`) that keeps only the recent quarters actually needed before it lands in context — never paste the raw multi-year JSON in.
- **Delegate ticker builds to a subagent** (already standard practice — see the wrap-up note about `/clear`-ing between tickers) so the heavy back-and-forth stays in that subagent's own context and the coordinating session's context stays flat. This matters just as much for a *post-build* fix/review pass done directly in the coordinating session (re-opening the finished file, taking verification screenshots) — the four bullets above apply there too, not just during the original build.

## Writing style — concise explanations (added 2026-09-05, after a cleanup pass across 8 existing tickers)

Every tab accumulates small-print explanations (caveats, methodology notes, "why does this number look surprising" asides). Write these tight from the start — don't rely on a later cleanup pass to catch bloat.

- **Keep**: anything that explains why a specific number looks the way it does (a distortion, an unusual pattern, a discrepancy between two numbers shown elsewhere on the page). This is the load-bearing content — don't cut it to save space.
- **Cut**: internal pipeline/implementation detail that doesn't help a reader interpret the number — file names (`valuation_signals.json`), script names (`compute_fundamental_score.py`), API/tag lookup mechanics ("companyconcept API 404 확인"), or exact intermediate arithmetic (exchange-rate/share-count walkthroughs) when only the conclusion matters. State the fact and its cause, not how you (the builder) derived it.
- **One fact, one primary home.** The same conclusion (e.g. "PBR is a weak comparison here," "a specific event/premium is a real, unresolved risk") tends to get restated near-verbatim in the box-key, 종합판단/종합밸류에이션, and the matching Bull/Bear item — this happened on BRK.B/MU/SKHY/V and had to be cleaned up after the fact. Pick ONE place to state it in full (usually the box-key or a dedicated card if the topic warrants one), and make every other mention a short pointer ("Bear 요인 참고", "위 카드 참고") rather than re-deriving the same explanation with the same numbers.
- **News timeline items: state the reaction and the interpretation, not the arithmetic that produced the reaction.** Write "발표 당일 +1.1% 소폭 상승했다" not "전일 종가 $362.53에서 당일 종가 $366.59로 +1.12%" — the reader needs the number and the causal read, not the two raw closes it came from. This applies to every `tl-desc`.
- **Default to one sentence per bullet/point** (box-key 01-04, Bull/Bear items) unless a second sentence adds a genuinely distinct fact. A bullet stacking 3+ clauses with em-dashes is a sign it's doing the job of two bullets.
- **Box-key HEADLINE sentence target: ~150-180 characters, check it with a character count before calling the tab done.** This is the single most repeated overshoot across builds (already had to be fixed after the fact on MA/XOM/INTC/LLY/JNJ/WMT/V on 2026-09-05, and again on KO on 2026-09-06) — the headline keeps growing past 220-250 chars because the builder tries to pack the growth numbers, every valuation multiple's premium %, AND the full risk description into one sentence, all of which are already stated in bullets 01/02/04 right below it. The headline's only job is the topline verdict + the one-line reason why (growth/strength clause — valuation conclusion — em-dash caveat, three clauses max); it should read as a compressed summary of the bullets, not a fourth restatement of their numbers. If a draft headline exceeds ~200 characters, that is the signal to cut specific figures out of it (they're already in the bullets), not to compress the sentence structure further.
- **Hard character budgets for every other long-form block, checked with `scripts/measure_verbosity.py <TICKER>` before calling the card done** (added 2026-09-09 after the user flagged PG; the same overshoot was present on NFLX/HD/GS simultaneously). The box-key headline rule above was the only length budget in this playbook, so every block it did NOT cover grew unchecked — 종합판단 bodies reached 470-520 chars, a single `tl-title` hit 246, a single `bb-item` hit 202. The budgets:
  - 핵심 가격대 `zone-list`: **max 5 rows**
  - 밸류에이션 + 뉴스 `verdict-summary-body`: **≤250 chars each**
  - `verdict-summary-risk` / `verdict-summary-counter`: **≤150** · `verdict-summary-next`: **≤120**
  - every `tl-title` and every `tl-desc`: **≤100**
  - every `bb-item`: **≤90**, one sentence
  Run `python3 scripts/measure_verbosity.py <TICKER>` from the repo root — it strips tags and prints each block's count against its limit. Do not eyeball these.
- **핵심 가격대 must not restate the 이동평균선 현황 card sitting next to it.** The two cards are a `grid-2` pair, so an MA row whose only content is a value already printed to its right is pure duplication. Keep 52주 최고 / 현재가 / 52주 최저 plus at most the nearest support and nearest resistance. **When several MAs cluster within ~1.5%, collapse them into ONE row** (e.g. PG's MA120 $145.86 / MA5 $146.56 / MA60 $147.24 all sat inside 1% and became a single `MA 저항 밀집 $145.86~147.24` row tagged `MA120·MA5·MA60 · 저항선`) — this both cuts rows and makes the clustering, which is the actual signal, visible instead of hiding it in three near-identical lines.
- **A fix that looks ticker-specific: derive its trigger condition and sweep, never judge whether other tickers "feel" extreme** (added 2026-09-10 after SNDK). The SNDK build found the shared chart boilerplate computing its y-axis floor as `mn - pad` with no lower bound, which printed a literal negative price label on a 34x price range. It was reported as "a latent bug in every card that no shipped ticker currently triggers" — an absence claim that was never tested. The trigger is one line of algebra (`bot = 1.06·mn − 0.06·mx`, negative once the displayed `max/min > ~17.67`), and sweeping it across every card's `*_DAILY` array takes seconds. Four views were already over it, and MU's 5-year chart had been rendering `$-24` on the live site the whole time. This is the same failure mode as the AVGO buyback note above: **absence in your analysis is not evidence of absence in the repo.** When you patch shared boilerplate in your own file, state the condition under which it fires and check every other card against it before calling the fix ticker-specific.
- **Before using "the last close", confirm that bar is a completed session** (added 2026-09-10). Two builds on the same day were briefed with, and one independently re-derived, prices taken from an in-progress intraday bar — the giveaway is volume far below the ticker's norm (GEV 384K vs ~1.5M; SNDK 3.4M vs ~10M). One was 4.3% off, which cascades into all five multiples, every gauge width, the 52-week position and the target band, and a partial bar can also move a period low (SNDK's 52-week low shifted $72.03 → $69.57 on truncation). Truncate the series to the last completed session, use that date on the card, and keep it consistent with sibling cards built the same day.
- **Never reconstruct a quarterly per-share figure by subtraction when the share count is moving.** SNDK's Q4 FY2026 diluted EPS comes out three different ways: $44.83 (annual minus the sum of three quarters), $44.34 (annual minus the tagged 9-month cumulative) and $43.97 (the figure the company reported). All three are arithmetically defensible and only the reported one is right, because the weighted diluted share count moved 145M→157M across the year. Use the company's own reported per-share figure; reconstruct revenue/income by subtraction if you must, but never EPS.
- **When trimming, cut duplication and never evidence.** Before deleting any figure, confirm it still appears elsewhere on the card and replace the restatement with a pointer (`상세 #fund`, `위 카드 참고`). A fact with no other home on the card stays — shrink the sentence around it instead. Never change a number's value to hit a budget, and never drop a GAAP-distortion or 평가 보류 caveat that a reader needs to interpret the multiples; if a block genuinely cannot fit because its content is irreducible, flag it rather than deleting substance.

If you're unsure whether something is "why the number looks that way" (keep) vs. an implementation detail or a restatement (cut), default to cutting and let the user ask if they want it back — this has never once gone the other way in practice.

## Step 0 — Pick the ticker

1. Confirm the current market-cap ranking via WebSearch/companiesmarketcap.com, cross-checked against at least 2 sources. Don't trust an old manifest order — rankings move.
2. Check whether a legacy widget exists at `prototypes/legacy/{TICKER}_analysis_widget.html` (only ADBE, CRM, HSBC, NVS, RHHBY — every other old widget already has a new card).
   - If yes: read it fully, use its content as the concrete starting point (do **not** re-fetch/re-research from scratch — reuse and re-verify what's there).
   - If no: build from scratch using the same data pipeline below (this repo's earlier `V`/rank-18+ precedent in the *old* live-repo project).

## Step 1 — Structural template

- Always 5 tabs, always built in this order: `#tech` → `#fund` → `#valuation` → `#news` → `#invest`.
- Use the most recently completed `{TICKER}_full_widget.html` in this repo as the structural template (check `projects/stock-widgets-redesign/progress_log.md` in the `second-brain` vault — archived there 2026-08-27, was `projects/stock-widgets/progress_log.md` — and the `project_stock_widgets_redesign_plan` Claude Code memory for which one is most current/refined).
- For the 2nd ticker onward, skip separate per-tab prototype files — build directly into `{TICKER}_full_widget.html`, tab by tab, full browser verification at the end of each tab. (NVDA used standalone prototypes first because the template itself was still being designed; that overhead isn't needed once the template is locked.)
- Copy the CSS block and shared JS utilities (`toggleCollapsible`, `showSection`, `renderCharts` controller, the candlestick-chart IIFE) from the template ticker, renaming ticker-specific IDs/prefixes (`aapl` → `googl`-style). **Double-check `toggleCollapsible` is actually included** even if you're only building `#tech` first — it's not needed until `#fund`'s collapsibles are clicked, so its absence won't show up until then, and only as a console error, not visually.
- **Set `--accent`/`--accent2`/`--accent3` to the new ticker's own real brand color — do not leave the template ticker's colors in place** (user-flagged 2026-09-06: 14 tickers had silently inherited NVIDIA's exact green `#76b900` this way, others a generic blue/orange, because copying the CSS block also copies its color values and nobody thought to change them). Source the color from the ticker's own `logos/{ticker}.png` if it already has real color in it (sample the dominant non-white/non-black pixel cluster) — this is more reliable than recalling a hex code from memory, which has produced wrong guesses before (e.g. assuming AbbVie is maroon when its real logo is navy blue). If the logo is monochrome (Apple, AMD's plain wordmark, JPMorgan, Lam Research, Micron, Palantir, etc.) or the company has no single distinctive brand color, pick a reasonable placeholder and say so explicitly in the Step 6 wrap-up rather than presenting it as verified. Generate `--accent2` (lighter) and `--accent3` (darker) via an HSL lightness shift from the new `--accent` — but clamp the result (roughly L 0.15–0.85) rather than a fixed delta, since a fixed shift pushed an already-dark navy (`--accent3`) to near-black on 4 tickers, making the active-nav-button background effectively invisible.
- **Fixed back-bar (added 2026-08-27, all 6 existing tickers have it):** every card needs the fixed top bar — `.back-bar` CSS + `body{padding-top:46px}` in `<style>`, and the `<div class="back-bar">...</div>` markup right after `<body>` (copy verbatim from any existing ticker, e.g. TSM). Left side links to `index.html`; right side is a rank-ordered prev/next chain across every existing ticker (`◀ {PREV}` / `{TICKER} · 시총 N위` / `다음 {NEXT} ▶`, `.disabled` span at either end of the chain). **Do not hand-patch the chain any more — run `python3 scripts/fix_backbar_chain.py` (add `--check` to verify without writing).** It regenerates every card's prev/next from `stocks.json`'s rank order, which is what the chain is supposed to mirror, and takes each card's display label from its own `back-bar-current` (BRKB's card calls itself BRK.B). Hand-patching two neighbours is what the playbook used to say and it failed twice without anyone noticing: by 2026-09-12 TSLA (rank 10) was orphaned in both directions because META pointed straight at BRK.B, and WMT (rank 16) still carried the disabled end-of-chain marker from when it was last, so every card from AMD onward was unreachable going forward — walking 다음 from rank 1 reached 15 of 54 cards. Ten more cards linked correctly but labelled the link `다음 ▶` with no destination, which looks exactly like the disabled end marker. Run the script against preview's cards first, then `sync_cards.py` brings the result here.

## Step 2 — Data pipeline

**Price data** (always, even if only building `#tech` first):
```
python3 scripts/fetch_price.py {TICKER} --range 5y --out data/raw_5y/{TICKER}.json
```
Always `--range 5y`, never `2y` — `2y` is enough for the tech-score calc but silently truncates the history the chart's 3Y/5Y range-toggle buttons need. This has already broken once (had to be re-fetched).

Then:
```
python3 scripts/compute_technical_score.py {TICKER} --price data/raw_5y/{TICKER}.json --out scripts/{TICKER}_tech_signal.json
python3 scripts/compute_breakout_signal.py {TICKER} --price data/raw_5y/{TICKER}.json --out scripts/{TICKER}_breakout_signal.json
```
Read the subscores/flags straight from the JSON output — don't hand-derive them.

**Known data-pipeline bug to route around:** `raw_5y/{TICKER}.json`'s `low52w`/`high52w` metadata fields are unreliable (computed over the wrong window, not a true trailing-252-day window). Always recompute the real 52-week high/low yourself by slicing the daily bars array to the last 252 entries directly — never trust the metadata field. **Both ends have now been wrong** (CRM and TMO, 2026-09-12/13); the older note here said `high52w` had always matched, which is no longer true, so recompute both.
  - **Take the INTRADAY extremes — the bars' own `high` and `low` — not the extreme closes.** The whole fleet does this (verified on AMGN, CRM, VZ, TXN, TMO), but it was never written down, so TMO matched AMGN's usage without knowing it was a convention and got there by luck. The two differ by more than a rounding: TMO's window gives intraday 647.00/435.27 against close-basis 639.45/438.34.
  - **Then quote every percentage off the same basis as the label.** TMO shipped a draft reading "5월 저점 $435.27 이후 +39.1%" — the price is the intraday low and the percentage was computed from the close low, which is +40.1% from the stated number. Codex caught it on the card and the same wrong figure had already been copied into the box-key headline. If the card names an intraday level, the move measured from it is intraday-based too.

**SEC EDGAR XBRL:**
```
curl -s -A "Mozilla/5.0 (research; contact <email>)" "https://data.sec.gov/api/xbrl/companyconcept/CIK{10-digit-zero-padded-cik}/us-gaap/{Tag}.json"
```
`WebFetch` gets a 403 from SEC EDGAR — always use `curl` with a descriptive User-Agent. Find the CIK via `https://data.sec.gov/submissions/CIK##########.json` (search) or the company's own EDGAR filing history page.

`companyconcept` returns the tag's *entire* multi-year history (often hundreds of entries) — pipe the `curl` output through a filter (`python3 -c "..."` or `jq`) that keeps only the recent quarters actually needed before it lands in context, rather than pasting the raw multi-year JSON in (see "Context/token efficiency" above).

Standard tag set fetched for every ticker's `#fund`/`#valuation`:
`Revenues` (or `RevenueFromContractWithCustomerExcludingAssessedTax`), `NetIncomeLoss`, `OperatingIncomeLoss`, `ResearchAndDevelopmentExpense`, `PaymentsToAcquirePropertyPlantAndEquipment` (Capex), `PaymentsForRepurchaseOfCommonStock` (buybacks), `NetCashProvidedByUsedInOperatingActivities` (OCF), `LongTermDebtNoncurrent`, `CashAndCashEquivalentsAtCarryingValue`, `MarketableSecuritiesCurrent`, `AssetsCurrent`, `LiabilitiesCurrent`, `InventoryNet`, `Assets`, `StockholdersEquity`, `Liabilities`, `EarningsPerShareDiluted`, `CommonStockDividendsPerShareDeclared`, `IncomeTaxExpenseBenefit`/`Income before provision for income taxes` (search the actual 10-Q text for the tax-rate table if the concept tag 404s — companies vary).

**Gotchas to check every time, not just once:**
- Fiscal-year misalignment (a company's Q4 may not map to a calendar quarter — derive it as FY-total minus 9-month-YTD if needed).
- Revenue/other tags can migrate over the years (e.g. `Revenues` → `RevenueFromContractWithCustomerExcludingAssessedTax`) — check for a switch rather than assuming one tag covers the full history.
- Some companies tag cash-flow-statement items as YTD-cumulative only (no discrete-quarter tag) in some quarters — always print the raw `start`/`end` pair before trusting a number's period, and derive the discrete quarter by subtracting consecutive YTD entries when needed.
- **Segment revenue is usually not in `companyconcept`** — fetch the actual 10-Q HTML (`curl` same as above) and grep for "Disaggregated Revenues" or the segment note's table.

**Analyst ratings** (for `#invest`): WebFetch both `stockanalysis.com/stocks/{ticker}/ratings/` and `stockanalysis.com/stocks/{ticker}/` — the ratings subpage often only shows a free-tier-truncated partial list, while the main page's consensus summary carries the real aggregate count/average target. Cross-validate the count and average against one more WebSearch before using either. Never invent a consensus figure from a partial list.

## Step 3 — Per-tab card checklist

Build in this order; each tab gets its own browser-verify + Codex-review pass before moving to the next.

### `#tech`
- Candlestick + volume SVG chart, range toggle `1M/6M/1Y/3Y/5Y`, MA5/20/60/120 toggle.
- 기술 상태 스코어카드 — read every number straight from `compute_technical_score.py`'s JSON output, don't hand-derive subscores.
- 핵심 가격대 + 이동평균선 현황 (`grid-2`). Verify the "N개 이평선 중 M개 상회" sentence against the actual MA values, and **order the 핵심가격대 zone-list rows by genuine descending price** — don't blindly copy the previous ticker's row order (52최고→MA선택→현재가→52최저 vs. 52최고→현재가→MA선택→52최저 depends on whether current price is above or below the featured MA that ticker).
- **Never add a "구간별 패턴 분석" card** (deprecated 2026-08-18, at the very start of this redesign — see the first progress-log entry). Chart-toggle + 스코어카드 근거불릿 already cover this; a separate card walking through date-range price swings is (a) explicitly retired scope and (b) duplicates `#news`'s own timeline almost verbatim. This regressed once on ORCL (2026-09-06, caught by the user, not by review) — grep the finished file for "구간별 패턴" before calling `#tech` done.
- **예상밴드 백테스트 오버레이 is a standard, expected part of every new ticker's `#tech` chart — do not skip it and do not forget to mention it in your build report.** Two real gaps happened this way: MRK shipped with the feature completely missing and unmentioned (caught by the user asking "백테스트가 없는데?"), and CSCO shipped with the toggle/JS already written but disabled behind a hardcoded `const visibleCheckpoints = [];` left over from an earlier attempt. Build it via `scripts/compute_earnings_backtest_band.py` (see that script's own docstring for the full methodology and `--exclude-per-window` usage) and transplant the toggle button + summary div + drawing code from the most recently completed ticker's `#tech` `draw()` function — it's copy-paste boilerplate, not something to write from scratch each time.
  - **The chart's y-axis scale must be computed from price/MA data only, never from the raw backtest predicted values** (fixed sitewide 2026-09-07 after the user caught MRK's chart looking broken — a single GAAP-distortion-quarter checkpoint had a predicted band up to $4,842 against an actual price under $160, which stretched the whole y-axis so far that the real price line compressed into an unreadable sliver). Instead: compute `priceMx`/`priceMn` from `highs`/`lows`/MA arrays only, then clip each checkpoint's drawn band (`cp._drawLow`/`cp._drawHigh`) to within `1.5×` the price span above/below that range before it can influence the scale or get drawn — a clipped box terminates at that boundary with a native SVG `<title>` tooltip showing the real unclipped range on hover, rather than distorting the chart for everyone. This is now baked into the standard boilerplate (see any ticker built 2026-09-07 or later, e.g. MRK) — copy it as part of the transplant, don't reintroduce the old unclipped version from an older card.

### `#fund`
- 분기 매출/순이익/OPM 8-quarter chart.
- FCF/Capex/R&D/다음실적 `grid-4` stat-boxes.
- 재무건전성 (안정성+활동성, collapsible detail toggles) — reuses the shared `toggleCollapsible` JS function; confirm it's actually present in the file (see Step 1).
  - **These rows must NOT use `.ma-row`** — that class belongs to `#tech`'s MA box and `pipeline/update_cards.py` counts it, asserting the count equals what its MA regex matched. CRM (rank 60) reused it for eight 재무건전성 rows and the card came back `failed — MA box: 12 rows, 4 in the expected format`, which means the daily run skips that card forever and its price layer freezes at build day while all the others move. Use `.fin-row` (rule copied verbatim from `.ma-row`, so the render is identical). **A build agent is card-only and cannot run the dry run that catches this, so check it with a grep you can run**: `grep -c '<div class="ma-row">' cards/{TICKER}_full_widget.html` must print exactly `4`, and every one of those four must carry a `ma-dot` span. The same caution applies to any class the pipeline counts — `.box-key` and the 핵심 가격대 title are the other two; `update_cards.py`'s `EditError` strings are the full list.
- YoY/QoQ 최신분기 비교 카드.
- 매출구성 도넛 + 자본배분·주주환원 + 다음실적체크포인트 (`grid-2`).
  - **자본배분·주주환원's ingredient set is fixed and Capex is not in it** (caught on AVGO, 2026-08-27): 배당액/자사주매입액/합계/잔여바이백한도/이벤트태그 only — this card is about cash actually returned to shareholders, not reinvestment. Capex/R&D belong in the `grid-4` stat-boxes above, or as a business-model note on the 매출구성 card (e.g. "fabless, asset-light → low Capex" is a fine one-sentence addition there). **Never write "회사가 자사주매입을 안 한다"/"배당·부채상환에만 쓴다" as a bare assertion — fetch the actual `PaymentsForRepurchaseOfCommonStock` (or equivalent) SEC XBRL figure and confirm it's genuinely ~$0 before saying so.** Absence of a number in your draft is not evidence of absence in reality — AVGO's card claimed no buybacks while the company had actually repurchased $8.45B in H1 FY26. **Don't add a 6th row for a derived ratio like "FCF 대비 %"** (caught on KO, 2026-09-06, user-flagged) — if that stat is worth stating, it belongs in the Bull/Bear box or the caveat paragraph below the card, not as an extra zone-list row; adding it to both the card AND a Bull bullet is the exact "one fact, one primary home" violation described above.
- If GAAP net income is distorted by a one-off item (equity revaluation, litigation charge, etc.), note it here with the real source figure — the adjustment itself happens in `#valuation`.

### `#valuation`
- 멀티플 5단계 평가 (PER/PBR/PSR/PCR/EV-EBITDA) + 피어비교 차트, side by side (`grid-2`).
- 종합 밸류에이션 as **compact synthesis prose**, not itemized rows — "itemize inputs, synthesize outputs" (a card that just re-tabulates numbers shown above it isn't earning its place; a synthesis card should state the derived judgment only).
- Anchor/peer group: prefer reusing already-built tickers' own verified multiples over fetching a brand-new peer, when the peer set is still reasonable for the comparison.
- **GAAP distortion check, every ticker:** compute GAAP PER from the real current price and TTM diluted EPS, compare it to whatever the legacy widget claims (if there is one). If there's a real one-off distorting EPS (equity-stake revaluation, litigation reserve swing, etc.), build an "adjusted PER" from TTM operating income × a clean effective tax rate (pick a quarter *before* the distortion for the "clean" rate), and show the raw GAAP figure only as a clearly-labeled, non-comparable secondary row.
- Gauge math: `width% = (value - low) / (high - low) * 100`, 5 stage bands split into equal fifths of `[low, high]`.
- **The val-item HTML and the JS data object (e.g. `MULTIPLE_DATA`) must state the exact same "적정 Nx" anchor figure** — this has been a real self-contradiction source (rounds differently in two places). Grep both for the same number before calling the tab done.

### `#news`
- "종합 해석" synthesis card first (지배적내러티브+tag, body, counter-signal, next-checkpoint) — same itemize/synthesize discipline as `#valuation`.
- **Verify every inherited timeline event's `tl-dot` color against the ticker's own daily price bars**, not the legacy widget's existing color. `neutral` is reserved for purely informational events with no real price reaction — an earnings beat/miss with a clear next-day move gets `green`/`red` even if the legacy widget marked it `neutral`.

Getting this backwards (using the report-day's own close instead of the *next* day's) is a real mistake that's happened before.
- Drop any "52주 최저/최고" framing on an event that's now more than ~1 year stale relative to the current `asOf` — state the historical fact without that label.

- **Every `tl-reaction` badge must show an actual number** (a %, or for a 52-week-high/low event specifically, the price level reached) — never a qualitative phrase like "주간 급락" or a category label like "투기등급 한 단계 위" standing in for the price move. If the event spans multiple days (a "worst week" story, a rating action followed by a slide into a later low), compute the real price change over the relevant window from the ticker's own daily-bar array and state it with its date range (e.g. `-19.4%(1주)`, `-20.6%(7.9→7.28 저점)`) — don't describe the move in words instead of pulling the number. This regressed on ORCL (2026-09-06, caught by the user) — grep the finished file for `tl-reaction` and confirm every value parses as a number or dollar price before calling `#news` done.

## How these cards actually go wrong (2026-09-13/14, from the STX, PEP and SCHW builds)

Five failure shapes that review kept missing. Each was found by recomputation, not by reading harder.

- **A compound claim is checked at the seams, not at the result.** PEP wrote "equity $22.10B is retained earnings $74.12B less treasury $42.15B less AOCI $14.34B" — the three operands give $17.63B; paid-in capital $4.47B was the omitted fifth line. It survived because everything *built* on $22.10B was right, so nothing downstream looked wrong. Same shape as "cheaper than all three peers on all five multiples", which was four. A sentence that reads as one claim is often several, and the conclusion being correct is exactly what lets a broken component through. **If a sentence hands the reader operands, add them up yourself.** SCHW shipped "3.00% NIM on $249.7B of deposits" next to net interest revenue that annualises to more than double what that multiplies to.
- **A redundant hardcoded copy keeps the conspicuous surface working while token-driven surfaces fail silently.** PEP lost `--ma5/--ma20/--ma60/--ma120` from `:root` in a colour edit; the MA toggle buttons and the four `ma-dot` spans rendered uncoloured through every screenshot while the chart drew correctly, because `draw()` carries its own `maColors`. Grep that every CSS variable a card references is still defined. The same build's `#fund` donut held the literal `#004b93` in its Chart.js array and its first legend swatch after `:root` had moved to `#03345a` — so a hardcoded duplicate can carry **the wrong brand's** value, not merely a drifted shade. After any colour change, grep the file for hex literals and assert the legend palette equals the chart palette element-for-element.
- **A template-inherited format can be conditionally correct, and the condition is invisible when the template satisfies it.** STX copied TMUS, which weights all five metrics at 1.0 and so legitimately carries no weight annotation on its badges. STX was the first card in that chain with non-uniform weights, and `build_valuation_base.py` reads the weight off the badge — so 0.5 parsed as 1.0. Before copying a format, ask what has to be true for it to be right.
- **A check that can only fail one way you imagined is weaker than one that recomputes the claim.** PEP's first gate for the above asserted a substring was absent, and failed on correct text; the replacement re-parses the printed operands and confirms they sum. The first would have passed a card with fixed wording and broken arithmetic.
- **Any partial-failure path that aborts before the write is indistinguishable from success if you read the script's output instead of the file.** Two builds hit this in one hour. Verify by reading the file.

Two conventions that follow from the above:

- **Compute a gauge fill from the band labels the card prints, not from full-precision internals.** Full precision is more accurate and less checkable, and for a card whose whole value is that a reader can verify it, checkable wins - the same principle as auditing with the source's own stated values. The DE build computed its fills from unrounded internals and two of four then failed to reproduce from the numbers printed beside them (PBR 70.6 against the labels' 70.33, PSR 95.9 against 96.09); stage 2B corrected both. 66 of 276 non-frozen gauges in the fleet still carry this, all under 0.6pp, which is exactly `baseline_test`'s tolerance - visually nil, and left alone rather than rewritten, but do not add to it.
- **Fixing one instance obliges a sweep for its class.** The same build printed `이자보상배율 15.3배` beside operands giving 15.52, fixed that one line, and walked past four gauge fills that were the identical failure sitting beside their own operands. The trigger condition here is one line: *any displayed percentage derived from values that are themselves displayed rounded.*
- **A figure that feeds a ratio stated elsewhere goes at full precision, in reports as well as on cards.** The rounded-threshold rule below is usually read as a rule about computing. It is also a rule about handing numbers to someone else: a build reported "tangible book $25.56B" in prose, the coordinator divided by it, and got 7.34 against the card's 7.33 - because $25.56B is 25,560M and the real figure was 25,564M. Half an hour went into checking for a share-count disagreement that did not exist. `$25,564M` costs three characters more and cannot be misused this way. If a number in a report is an input to something else in that report, give it unrounded or not at all.
- **State a rank, not a percentile,** when placing a value inside its own series — "529일 중 150위", not "71.8 백분위". Ranking an observation inside its own series against the *rounded display value* destroys the self-tie, which is the only place the inclusive and exclusive conventions differ; both then agree and the check reports an agreement it never tested. A rank uses strict comparison only and a reader can reproduce it. At large n the percentile is safe (at n=1,255 one observation is 0.08pp) but say which comparison it uses.
- **Mark a forecast as conditional on the claim itself, not beside it.** "MA150 and MA200 cross in three sessions" is only true at a flat price. A reader who watches it not happen should be able to tell the price moved rather than that the card was wrong.

## Step 4 — Codex review protocol (every tab)

- **Text mode only**, always: `codex exec --skip-git-repo-check -` (keeps the per-tab review workflow consistent; code-mode `codex review --uncommitted` isn't part of this process even now that the repo has a remote).
- Package for each round: the tab's own HTML **plus any JS data object that drives that tab's dynamic content** (critical for `#valuation`'s `MULTIPLE_DATA` — the static HTML alone is nearly empty since JS fills it at runtime) **plus a clearly labeled "검증된 원본 데이터" block listing every number Codex might want to cross-check**, including full peer/comparison tables. An incomplete fact package causes false positives that waste a review round (documented repeatedly across AAPL and GOOGL sessions).
- Always include: "절대로 파일을 읽거나 저장소를 탐색하지 마세요 — 아래에 붙여넣은 내용만 검토하세요." Codex has workspace-write access and will otherwise go explore the repo when a prompt sounds like it should route through a skill.
- **Independently re-verify every finding before applying it.** Codex has been both right (catching real self-contradictions, date-pairing errors, rounding mismatches) and wrong/overly conservative (flagging a correct, well-grounded causal claim as "unverifiable" purely because that specific sub-fact wasn't in the review package). Rejecting a finding is fine and expected — just verify independently first, don't rubber-stamp either direction.
- Cap at 3 rounds per tab. If not converged by then, stop and report status instead of continuing silently.
- **Round 2/3 payload is a diff, not a resend.** Round 1 sends the full package described above. If Codex flags issues and needs another round, send only the changed lines plus whatever specific facts are needed to re-verify them — not the entire tab+data package again (see "Context/token efficiency" above).

## Step 5 — Browser verification protocol (every tab)

- Before opening a browser: div-tag balance check (`<div` count vs `</div>` count) and `node --check` on the extracted `<script>...</script>` block.
- `claude-in-chrome` blocks `file://` URLs outright. Serve the repo with `python3 -m http.server {port}` and navigate to `http://127.0.0.1:{port}/{TICKER}_full_widget.html`. Kill the server (`pkill -f "http.server {port}"`) when done.
- **Click-after-scroll (or click-after-navigate) is unreliable** — it silently lands on stale coordinates often enough to be a reliable pattern, not one-off flakiness. Always: scroll as its own tool call → screenshot to confirm the settled layout → click as a separate subsequent call. Never chain them in one batch and trust pre-scroll coordinates.
- Check console errors (`onlyErrors: true`) after every meaningful interaction — tab switch, collapsible toggle, val-item click, range-toggle click. A `ReferenceError` for a missing shared function (see Step 1) only shows up here, never visually.
- **Screenshot budget, per tab: one confirming shot after the layout has settled**, not one per scroll tick or per thing being checked. Batch the scroll(s) needed to reach a target position into as few tool calls as possible before the confirming screenshot; if a click changes something that needs visual confirmation, that's a legitimate second shot, but don't re-screenshot a region that already rendered correctly in a prior shot. Use `zoom` on a specific region instead of a fresh full-page screenshot when inspecting a small detail closely.

## Step 5b — Join preview's daily pipeline (added 2026-09-11, required for every new card)

Since 2026-09-11 `stock-widgets-preview` updates itself after every US close (GitHub Actions `.github/workflows/daily_refresh.yml`, 18:00 New York / 07:00 Seoul, Mon–Fri). `site_data/stocks.json` is the homepage's source of truth — `pipeline/build_index.py` renders `index.html` from it, so **never hand-edit the DATA rows between `/*STOCKS_DATA_START*/…/*STOCKS_DATA_END*/` again** — and `pipeline/update_cards.py` rewrites every listed card's price layer (DAILY/MA arrays, header, chart summary, tech scorecard, MA box, as-of label). A new card has to join that pipeline in the same commit that adds it:

1. **Pull first**: `git pull --rebase`. The Actions bot pushes to preview `main` every trading day; don't commit around 18:00–18:10 ET.
2. **Add the card and its `stocks.json` entry together.** `validate_site_data.py` requires the set of `*_full_widget.html` files to equal the `href` list — a card without an entry (or an entry without a card) makes the next daily run fail at "Build and validate". Append an entry with the next `cardRank` (ranks must run 1..N with no gaps) and placeholder price/shares that the scripts below replace:
   ```json
   {"ticker": "KLAC", "name": "…(Korean name)", "sector": "…", "href": "KLAC_full_widget.html", "cardRank": 51,
    "cardAsOf": "YYYY-MM-DD (the card's analysis date)", "listing": {"type": "common"},
    "price": {"close": null, "status": "unavailable", "statusReason": "new card - first fetch pending"},
    "shares": {"usEquivalent": 1306546783, "method": "sec-cover", "basis": "single",
               "asOf": "YYYY-MM-DD", "filedAt": "YYYY-MM-DD", "status": "unverified"},
    "tier": {"value": "고평가", "raw": "고평가", "status": "valid"},
    "score": {"status": "missing", "reason": "no score file (card built after the 2026-08-25 scoring run)"}}
   ```
   `shares.usEquivalent` = the SEC count the card itself uses (a positive integer is required even as a placeholder). `tier.value` = the card's 7-tier headline label. Add `"yahooSymbol"` only when Yahoo's symbol differs (BRKB → `BRK-B`). Multi-class and ADR cards: copy the `listing`/`shares` shape from an existing example (GOOGL, V, BRKB for classes; TSM, SKHY for `adr` + `adrRatio`).
3. **Append the tier to `site_data/tier_history.json`**: `{"ticker": "KLAC", "evaluatedAt": <cardAsOf>, "stages": null, "weights": null, "weightedAvg": null, "machineTier": null, "previousTier": null, "publishedTier": <tier.value>, "decision": "seeded", "ruleVersion": "card-headline-v0"}`.
4. **Fill the real values** (each is a dry run without `--write` — read the output first):
   - `python3 pipeline/seed_shares.py --tickers KLAC --write` — replaces the placeholder with the verified SEC record and flags a large gap from it (investigate a flag; don't just accept it). **A silent gap is not a safe gap**: its `FLAG_GAP` is 5%, and Citigroup's stale reading came in at 4.29% with no warning printed at all, which would have swapped a verified count for a seven-month-old one and reversed two ranks. Since 2026-09-12 the script refuses any incoming record whose as-of date is older than the one already stored, whatever the gap — but read the printed as-of date yourself rather than trusting the absence of a flag.
   - `python3 pipeline/fetch_prices.py --tickers KLAC --write`
   - `python3 pipeline/build_index.py && python3 pipeline/validate_site_data.py` — must end with "OK".
5. **The card must pass the updater**: `python3 pipeline/update_cards.py --tickers KLAC` (dry run) must say `updated` or `unchanged`, never `failed` or `held` — read its reason if it does. **This is the cheapest check in Step 5b and the one whose failure is quietest**: `failed` means the daily run skips that card forever, so its price layer freezes at build day while all the others move, and the card still renders perfectly in a browser with no console error. CRM (rank 60) tripped it by reusing `.ma-row` for eight 재무건전성 rows in `#fund` — the updater asserts that the `<div class="ma-row">` count equals what its MA regex matched, so 12 rows against 4 matches was a hard failure. **Never reuse a class the pipeline counts** (`.ma-row`, `.box-key`, the 핵심 가격대 title); when you want the same look, copy the rule into a new class (`.fin-row`) — identical rendering, invariant preserved. The `EditError` strings in `update_cards.py` are the list of what it counts. It relies on the standard markup, so copy these blocks from a recent card (ANET) rather than improvising: one-line `const {T}_DAILY = [[date,o,h,l,c,v],…];` plus `{T}_MA5/20/60/120` arrays of the same length, each on its own line; header `price-main`, `price-change` "(YYYY.MM.DD 기준)", the "52주 최저 … · 최고 …" line and the 시가총액 meta item; `techHeaderTitle` and `techRangeSummary`; the tech scorecard (subtitle "가격·거래량 기반 기술 상태 점수 (모델 v1.0.0 · YYYY-MM-DD 기준)", 3 subscore boxes, breakout badge, 기준일 footer); the MA status rows; exactly one `<div class="box-key">` and one `핵심 가격대` card title. Then run it once with `--write`: it inserts the as-of label and the 핵심 가격대 analysis date and creates `site_data/tech_state/{T}.json` (the tech score's hysteresis state).
6. **Record the card's valuation baseline**: `python3 pipeline/build_valuation_base.py --tickers KLAC --write`, then read the audit row it prints - it says which multiples will follow the price daily and which are frozen (withheld badges, a metric with no EV stated, and so on). Without this file the card's valuation tab never moves: `update_cards.py` only touches a tab it has a baseline for, so a new card would sit at its build-day multiples while every other card updates. The baseline has to be taken **before** the card's valuation tab has ever been updated - `build_valuation_base.py` refuses a card that already carries stage-2B marks. P0 comes from the card's own header for a card added after stage 2A (older cards read it from git commit e68eda0).
7. `python3 pipeline/test_pipeline.py` must still pass. Commit the card, `site_data/stocks.json`, `site_data/tier_history.json`, `index.html`, `site_data/card_status.json`, `site_data/tech_state/{T}.json` and `site_data/valuation_base/{T}.json` together.

**Two guards in this stage used to fire on wording rather than on state; both were fixed 2026-09-13, and the reason is worth carrying.** `build_valuation_base.py` decided "stage 2B already moved this card" by finding `(분석일 YYYY.MM.DD 기준 계산)` anywhere in the HTML — which is exactly what a build agent writes by hand, so it blocked five consecutive brand-new cards (TXN, LIN, CRWD, VZ, AMGN) and each was worked around by rewording the card. It now also requires `site_data/valuation_base/{T}.json`, the condition `update_cards.py` actually branches on, so a card without a baseline provably has never been touched by 2B. Separately, `valuation.py` only recognised an anchor as-of introduced by `, ` or `(앵커 `, so a card writing `평균 27.23x· 2026.09.11 기준` got a second date appended and shipped reading `…기준, 2026.09.11 기준)` (CRM, LIN, CRWD). **The general rule: a script must never detect "have I already run here?" by searching for a string a human also writes — bind it to the state the behaviour branches on. And if you find yourself rewording a card to satisfy a check, stop and fix the check.**

## Standardized valuation-verdict label system (locked 2026-08-27, via Codex methodology consultation + final review, rolled out to all 7 tickers)

Three **independent, non-interchangeable** label systems now exist. Never let one influence another's wording, and always keep each visually distinct (a bare badge with no context risks reading as a contradiction — pair it with the number/axis it came from, e.g. "3.8/5단계(고평가 쪽) — 고평가", not a floating "고평가" alone).

**1. 핵심 투자 논리 headline / 종합밸류에이션 tag / 4개분석종합 밸류에이션 row** — same fixed 7-tier label in all three spots: 초고평가·고평가·고평가~적정·적정·적정~저평가·저평가·초저평가. Color: 초고평가/고평가=red, any label containing "적정"=gold, 저평가/초저평가=green (do not shade within gold — user specified exactly 3 color buckets, deliberately).
  - **Hybrid computation** (Codex-designed, re-verified 2026-08-27): average the 1–5 stage badges of the 5 multiples (PER/PBR/PSR/PCR/EV-EBITDA), weight 1.0/0.5/0 per metric by reliability — 0 only when the card's own body says the comparison is literally not meaningful (different basis, e.g. AMZN's P/OCF-vs-peer-P/FCF; already-withheld "평가보류" metrics like AVGO's PCR), 0.5 when the body documents a real but partial distortion (structural, not "the premium is deserved" — that argument is explicitly NOT grounds for exclusion). Map the (weighted) average onto the 7 bins (equal-width over [1,5], bin edges at 1.571/2.143/2.714/3.286/3.857/4.429).
  - **Max 1-tier adjustment, only when justified**: if the weighted average and the card's own already-established conclusion land in the same or adjacent bin, no further adjustment. If they diverge by 2+ bins, don't auto-resolve — read the actual body text and manually decide, capped at one tier of movement from the mechanical anchor; if the body explicitly *rejects* a "premium is justified" framing (TSM's "설명될 뿐 크기까지 정당화되진 않았다"), do not soften the label just because a justification-shaped sentence exists nearby.
  - Any per-metric nuance/caveat that used to live inline in the headline sentence stays there or moves to the existing pill pattern (e.g. "밸류에이션 · PER 34.3x") — don't invent new pills where a plain number update suffices.

**2. `#tech` tab 3-tier badge** — 기술적 분석 우수(점수≥85) / 적격(60–84) / 부적격(<60), replacing the old raw `displayGrade` text in the `.scorecard-grade` badge (reuses the same badge slot/styling, doesn't add a second one). Pure function of `rawScore` — no judgment calls.

**3. `#valuation` tab 3-tier badge** — 저평가(combinedStage<2.33) / 적정(2.33–3.67) / 고평가(≥3.67), computed purely from the fundamental score's own `valuation.combinedStage` (already in each ticker's saved `{TICKER}_fundamental_score.json`, weights PER+PBR+targetPrice stage only — not the 5-metric set used in system 1). Zero narrative judgment — append as a colored `<span>` right after the existing subscore-desc sentence, matching the pattern `— <span style="color:var(--gold);font-weight:700;">적정</span>`. **This will disagree with system 1 sometimes** (different inputs, different math) — that's expected and correct, not a bug to reconcile.

## Full-repo price/data refresh procedure (used 2026-08-27, first time this scale)

**In preview this is now mostly automatic (2026-09-11):** `pipeline/update_cards.py` refreshes the DAILY/MA arrays, header price/change/52-week line/market cap, chart title and range summary, tech score, MA status box and as-of label for every card every trading day — do not hand-refresh those there, and never regenerate the MA arrays wholesale (the updater keeps stored values and only appends). The manual steps below still apply to redesign and to what the updater doesn't touch: the `#valuation` multiples and gauges, the target-band marker (automation planned as stage 2B), and analysis prose that quotes prices.

- `fetch_price.py {T} --range 5y --out data/raw_5y/{T}.json` per ticker (this repo's own `scripts/fetch_price.py`, copied from the retired old repo on 2026-09-11 — it only reads Yahoo and writes `--out`).
- Splice the fresh `daily` array into each ticker's embedded `{T}_DAILY` JS array via a small regex-replace script (never hand-retype) — verify tail date/close before and after.
- **Also regenerate `{T}_MA5/20/60/120`** (the separate precomputed rolling-SMA arrays that drive the chart's MA lines) from the same fresh daily closes, same script pattern. **Missing this step was a real bug this session** — the chart draws by slicing `_DAILY` and each `_MAn` array by the same trailing count and pairing by index, so stale/mis-length MA arrays silently misalign or show pre-refresh values on the most recent day(s) even though the candlesticks themselves look right. Cross-check each array's new tail value against the MA figure you're independently using elsewhere on the page (ladder/MA-row text) — they must match exactly.
- Recompute technical score (`compute_technical_score.py`) and the 5 valuation multiples (same anchors/BPS/SPS/EPS as before, just new price) by hand — reuse the existing `[low,high]` band edges and **do not re-derive stage badges from a formula** (none exists; they were hand-set at build time). Only move a stage badge if the new width% obviously crosses into a different visual band the card already shows for a neighboring stage.
- A single day's price move can be a real news event (NVDA jumped +7.4% on 08-27 from Q2 FY27 earnings reported after-close 08-26) — WebSearch to confirm before treating it as routine drift, and fix any now-stale "다음 실적: (예상)" stat box that already happened.
- Recompute real MA50/150/200 directly from daily closes (`sum(closes[-n:])/n`) for the `#tech` evidence-bullet prose whenever citing exact dollar values — the tech-signal JSON only exposes MA5/20/60/120, not the scoring MAs.
- Sweep for secondary mentions of a refreshed number outside the 3 primary label locations — Bull/Bear box bullets, anchor-card cross-notes, 투자의견요약 stat-sub, target-band marker `left:%` position (recompute from the Bear/Base/Bull price-range labels' implied linear scale, not just the price text) all silently go stale on a `replace_all` of the price string alone.
